# CSRF란?

로그인한 사용자의 쿠키를 다른 사이트가 몰래 빌려쓰는 공격

---

## 공격 흐름

1. 사용자가 bank.com에 로그인되어 있음
2. 공격자가 attacker.com 함정 페이지를 만들어둠 (페이지 안에 bank.com으로 요청 보내지는 숨겨진 폼)
3. 공격자가 메일/메신저로 attacker.com 링크를 사용자에게 보냄
4. 사용자가 그 링크를 클릭 → attacker.com 도착
5. attacker.com 페이지가 로드되자마자 JS가 자동으로 폼 제출  
   (사용자는 아무것도 안 했는데 bank.com으로 송금 요청 발사)
6. 사용자 브라우저가 bank.com 쿠키를 자동 첨부
7. bank.com: 정상 사용자네 → 송금 실행
8. 공격자 계좌에 돈 도착

---

## 송금 말고도 아래 예시들이 있다

- 은행: 송금, 카드 발급, 한도 변경
- 쇼핑몰: 사용자 변경, 자동 주문, 카드 등록
- SNS: 게시글 작성, 친구 삭제, 비밀번호 변경, 이메일 변경
- 관리자: 사용자 권한 변경, 데이터 삭제, 설정 변경
- 공유기: DNS 변경

---

## CSRF를 막는 방법

1. **CSRF 토큰** — 서버 차원의 방어. 서버가 발급하는 일회용 비밀번호  
   서버가 폼에 토큰을 심어두고, 요청 시 그 토큰이 없거나 틀리면 거부
2. **SameSite 쿠키** — 브라우저 차원의 방어. 쿠키에 박는 속성으로, 브라우저가 요청을 보낼 때 출발지를 보고 쿠키를 자동 첨부할지 말지 결정하는 데 쓰임  
   서버가 `Set-Cookie` 헤더에 SameSite 속성을 붙여 내려주면, 브라우저가 그 규칙을 기억해두고 실행하는 구조 (서버가 규칙 설정, 브라우저가 실행)
   - `Strict` — 다른 사이트에서 온 요청엔 쿠키 아예 안 보냄
   - `Lax` — 다른 사이트 GET 링크 클릭엔 허용, POST 같은 상태 변경 요청엔 차단
   - `None` — 모두 허용 (반드시 `Secure`랑 같이 써야 함)

둘 다 "우리 사이트에서 출발한 게 맞는지" 확인한다.  
SameSite는 브라우저 차원 방어, CSRF 토큰은 서버 차원의 방어
