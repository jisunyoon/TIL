# 프로세스 · 스레드 · 메모리 구조 · GC

프로그램이 실행돼 프로세스가 되고, 그 안의 스레드가 메모리를 공유하며 코드를 실행한다 — 그 구조와 JS 엔진 동작 원리

---

## 프로그램 vs 프로세스 vs 스레드

| 용어 | 뜻 |
|---|---|
| **프로그램** | 디스크에 저장된 **정적인 코드 덩어리**. 아직 안 돌고 있는 설치된 앱 |
| **프로세스** | 프로그램이 실행돼 **메모리에 올라간 상태**. OS가 독립된 메모리 공간과 자원을 할당한 실행 단위 |
| **스레드** | 프로세스 안에서 **실제로 코드를 실행하는 흐름**. 한 프로세스에 여러 개 가능, 메모리 공유 |

> 프로그램은 **레시피**, 프로세스는 그 레시피로 **실제 요리하는 것**, 스레드는 **요리하는 손**.
> 손이 여러 개면 멀티스레드.

### 소프트웨어 → 하드웨어로 내려가는 층위

```
프로그램 (파일)            ← 소프트웨어
    ↓ 실행
프로세스 (메모리에 올라감)  ← 소프트웨어
    ↓ 안에
스레드 (실행 흐름)         ← 소프트웨어
    ↓ OS가 배치 (스케줄링)
코어 (실제로 굴림)         ← 하드웨어
```

- **프로그램 · 프로세스 · 스레드**까지는 전부 **소프트웨어** 개념
- **코어**는 실제로 연산을 굴리는 **하드웨어**
- 그 사이를 **OS의 스케줄링**이 이어줌 → 어떤 스레드를 어느 코어에 언제 올릴지 배치

> 즉 스레드는 "실행 흐름(할 일)"일 뿐이고, 그걸 **실제로 돌리는 건 코어**. OS가 둘을 연결한다.

## 프로세스 메모리 4영역

```
높은 주소
┌─────────────┐
│    Stack    │  ↓ 아래로 자람  (함수 호출: 지역변수·매개변수·복귀주소)
├─────────────┤
│      ↕      │
├─────────────┤
│    Heap     │  ↑ 위로 자람    (동적 할당: 객체·배열)
├─────────────┤
│    Data     │  전역변수·static (프로그램 시작~끝 생존)
├─────────────┤
│ Code(Text)  │  실행할 기계어 코드 (읽기 전용)
└─────────────┘
낮은 주소
```

| 영역 | 저장되는 것 | 관리 |
|---|---|---|
| **Code(Text)** | 실행할 기계어 코드 | 읽기 전용 |
| **Data** | 전역 변수, static 변수 | 시작~끝까지 생존 |
| **Heap** | 동적 할당 (객체·배열) | GC / 개발자 |
| **Stack** | 함수 호출 정보 (지역변수·매개변수·복귀주소) | 함수 끝나면 자동 해제 |

> **Code·Data·Heap은 스레드끼리 공유, Stack만 스레드마다 따로.** 이게 멀티스레드의 핵심.

## 동시성(Concurrency) vs 병렬성(Parallelism)

| | 동시성 (Concurrency) | 병렬성 (Parallelism) |
|---|---|---|
| **정의** | 여러 작업을 **번갈아** 처리해 동시처럼 보이게 | 여러 작업을 **진짜 물리적으로 동시** 처리 |
| **실제 실행** | 한 번에 하나 (번갈아) | 진짜 동시에 여러 개 |
| **필요한 코어** | **1개여도 됨** | **2개 이상 필수** |
| **비용** | 컨텍스트 스위칭 오버헤드 | 스위칭 불필요 |
| **비유** | 화구 1개로 요리 3개 번갈아 | 화구 3개로 요리 3개 동시에 |
| **JS 예시** | 이벤트 루프 (싱글스레드로 번갈아) | Web Worker + 멀티코어 |

> JS 메인 스레드는 싱글스레드라 **동시성**으로 동작하지만, **Web Worker**를 쓰면 병렬 처리도 가능하다.

> **컨텍스트 스위칭**: 스레드를 번갈 때 현재 상태(레지스터·PC)를 저장하고 다음 걸 불러오는 작업.
> 공짜가 아니라서 **너무 자주 하면 오히려 느려짐**.

## 멀티프로그래밍 / 멀티태스킹 / 멀티프로세싱 / 멀티스레드

헷갈리기 쉬운 네 용어. **서로 다른 축**의 얘기라 기준을 나눠 봐야 한다.

| 용어 | 무엇을 여러 개 | 어떻게 | 핵심 |
|---|---|---|---|
| **멀티프로그래밍** | 프로그램 | 하나가 **I/O 대기하면** 다른 걸 실행 | CPU 안 놀게 |
| **멀티태스킹** | 작업(태스크) | 아주 짧게 **번갈아**(시분할) | 동시처럼 보이게 (=동시성) |
| **멀티프로세싱** | 프로세스 + **코어** | 코어 여러 개로 **진짜 동시** | 진짜 병렬 (=병렬성) |
| **멀티스레드** | 스레드(실행 흐름) | 한 프로세스 안 여러 흐름, **메모리 공유** | 가볍게 병렬 |

**발전 순서** (프로그래밍 → 태스킹 → 프로세싱):

```
① 멀티프로그래밍 — A가 I/O 대기하는 동안 CPU가 B 실행 ("CPU 놀리지 말자")
② 멀티태스킹    — 아주 짧게 번갈아(시분할) → 동시처럼 보임 (코어 1개여도)
③ 멀티프로세싱  — 코어 여러 개로 A·B를 진짜 물리적 동시에
```

**①과 ②의 차이 = "번갈아 도는 계기"** (둘 다 여러 개를 번갈아 쓴다):

| | 번갈아 도는 계기 |
|---|---|
| **멀티프로그래밍** | 하나가 **I/O 대기할 때만** 넘어감 (양보식) |
| **멀티태스킹** | **시간을 쪼개**(시분할) 강제로 짧게 번갈아 |

> 주의 — 쪼개는 건 **프로세스가 아니라 CPU 시간.** 시간을 잘게 나눠 각 프로세스에 짧게 번갈아 배정하는 것.
> 그래서 멀티태스킹은 멀티프로그래밍의 **발전형** ("대기할 때만" → "아예 짧게 쪼개서").

**멀티스레드는 축이 다름** — 앞 셋이 "CPU가 작업을 **어떻게 굴리냐**"라면, 멀티스레드는 "실행 흐름의 **단위**" 얘기:
- **멀티프로세스** = 프로세스(독립·메모리 분리) 여러 개
- **멀티스레드** = 한 프로세스 **안에서** 스레드(메모리 공유) 여러 개

> 연결: **멀티태스킹 = 동시성**(번갈아), **멀티프로세싱 = 병렬성**(진짜 동시). 위 동시성/병렬성 표와 같은 얘기.

## 멀티프로세스 vs 멀티스레드 — 언제 뭘 쓰나

**같은 기준(축)으로 비교** — 한쪽의 장점이 곧 다른 쪽의 단점이다.

| 기준 | 멀티프로세스 | 멀티스레드 |
|---|---|---|
| **안정성·격리** | ✅ 좋음 (하나 죽어도 나머지 멀쩡) | ❌ 약함 (하나가 메모리 오염시키면 같이 죽음) |
| **무게·속도** | ❌ 무거움 (생성·전환 비용 큼) | ✅ 가볍고 빠름 |
| **통신** | ❌ 어려움 (메모리 분리 → 통신 비용 큼) | ✅ 쉬움 (메모리 공유) |
| **동기화** | 불필요 (메모리 안 공유) | ❌ 필요 (락·뮤텍스로 race condition 방지) |
| **예시** | 크롬 탭 분리 (탭 하나 뻗어도 브라우저 안 죽음) | 한 프로세스 내 병렬 계산 |

> 요약: **멀티프로세스 = 안전하지만 무겁다**, **멀티스레드 = 가볍고 빠르지만 위험하다(같이 죽고 동기화 필요)**.
> 핵심 원인은 **메모리 공유 여부** — 안 나누면(프로세스) 안전한 대신 통신이 비싸고, 나누면(스레드) 빠른 대신 서로 간섭한다.

## Race Condition & 데드락

### Race Condition (데이터 레이스)

두 스레드가 공유 메모리에 동시에 써서 **실행 순서에 따라 결과가 꼬이는 것.**

**두 조건이 동시에 만족될 때만** 생긴다:
1. 여러 스레드가 동시에/번갈아 실행됨 (동시성·병렬성)
2. **+ 같은 메모리를 공유해서 씀** (스레드는 Heap·Data 공유)

> 하나만으론 안 생김 — 각자 다른 메모리만 건드리면 충돌 없고, 같은 메모리라도 한 번에 하나씩(순서 보장)이면 안 꼬임.

```
count = 0  (두 스레드가 같이 +1)

A: count 읽음 (0)
B: count 읽음 (0)   ← A가 저장 전인데 B가 끼어듦
A: 0+1=1 저장
B: 0+1=1 저장       ← 2가 돼야 하는데 1! (하나 증발)
```

→ **락·뮤텍스·세마포어**로 "한 번에 하나만 건드리게" 막는다.

### 데드락 (교착)

레이스를 막으려 건 **락 때문에 생기는 또 다른 문제.** 두 스레드가 서로가 쥔 락을 기다리며 **관련된 스레드가 다 같이 영원히 멈춤.**

```
A: 1번 락 잡음 → 2번 락 기다림  ┐
B: 2번 락 잡음 → 1번 락 기다림  ┘  서로 물림 → 둘 다 영원히 멈춤
```

- 핵심은 **순환 대기** — 상대가 놓아야 내가 푸는데, 상대도 나 때문에 못 푼다
- **한 개만** 멈춘 거면 데드락 아님 (돌아가는 쪽이 끝내고 락 놓으면 결국 풀림). 아무도 못 놓아서 영영 안 풀리는 게 데드락
- 이름 그대로 dead(죽은) + lock(잠금) = **잠긴 채 멈춰버림**

### 셋의 관계

```
레이스 컨디션 (문제 ①)
    ↓ 막으려고
락(lock) (해결책)
    ↓ 잘못 걸면
데드락 (문제 ②)
```

| | 원인 | 증상 |
|---|---|---|
| **레이스 컨디션** | 락을 **안 걸어서** | 결과가 꼬임 |
| **데드락** | 락을 **잘못 걸어서** | 관련 스레드 다 같이 멈춤 |

> 락은 **안 걸면 레이스, 잘못 걸면 데드락** — 그 사이에서 조심히 다뤄야 한다.

## JS 싱글스레드 → 왜 블로킹?

JS 메인 실행은 **스레드가 하나(콜 스택 하나)**.

- **장점**: 공유 메모리에 동시에 쓰는 스레드가 없어서 **데이터 레이스가 원천적으로 없음**(락 불필요).
- **단점**: 그 하나뿐인 스레드가 무거운 동기 작업(큰 루프·무거운 계산)을 잡으면 그동안 **렌더링·이벤트가 다 멈춤 = 블로킹**.

→ 그래서 무거운 건 **비동기(이벤트 루프)로 미루거나 Web Worker로 넘김.**

> 단, 비동기라도 순서가 안 보장되는 **논리적 race condition은 있을 수 있음** — 나중에 쏜 fetch가 먼저 도착하는 경우.

### 블로킹 vs 데드락 — 헷갈리지 말 것

| | 블로킹 | 데드락 |
|---|---|---|
| **어디서** | **싱글**스레드 (손 하나) | **멀티**스레드 (락 얽힘) |
| **원인** | 무거운 작업이 하나뿐인 손을 붙잡음 | 락을 잘못 걸어 서로 기다림 |
| **상태** | 그 작업 끝나면 **다시 풀림 (일시적)** | 아무도 안 놓아 **영영 안 풀림 (영구적)** |

```
블로킹:  무거운 작업 실행 중... [멈춤] → 작업 끝 → 다시 돌아감  (일시적)
데드락:  서로 락 기다림...      [멈춤] → 영원히 안 풀림          (영구적)
```

> 제일 큰 차이 = **풀리냐 안 풀리냐.** 블로킹은 끝나면 알아서 풀리고, 데드락은 서로 기다려 영영 안 풀린다.

### Web Worker — 블로킹 피하기

무거운 계산을 **별도 스레드**에서 돌려 메인 스레드(손 하나)가 안 막히게 하는 것. JS를 멀티스레드처럼 쓰게 해준다.

```
[기존]     메인 스레드 하나          ← 무거운 계산하면 여기서 막힘(블로킹)

[Web Worker]
   메인 스레드  ←(메시지 복사)→  워커 스레드
   (화면·이벤트, 안 막힘)         (무거운 계산 전담)
```

싱글스레드를 멀티로 바꾸는 게 아니라, **메인은 그대로 두고 일할 스레드를 하나 더 붙이는** 것.

```js
// 메인
worker.postMessage(bigData);        // 워커에 일 넘김
worker.onmessage = (e) => { ... };  // 결과 받음

// 워커(worker.js)
onmessage = (e) => {
  const result = 무거운계산(e.data);
  postMessage(result);              // 결과 돌려줌
};
```

**멀티스레드와 다른 점:**

| | 일반 멀티스레드 | Web Worker |
|---|---|---|
| 메모리 | Heap/Data **공유** | **공유 안 함** |
| 통신 | 공유 메모리 직접 | **메시지 복사** (postMessage) |
| race condition | 있음 (락 필요) | **없음** (공유 안 하니까) |
| DOM 접근 | - | **불가** (순수 계산만, 화면은 메인이) |

> Web Worker = 메모리 공유 대신 **복사로 통신하는 안전한 멀티스레드.**
> 병렬 처리 장점은 얻고, race condition 단점은 피한다.

## 스택/힙 + 원시값/객체

| | 저장 위치 | 대상 |
|---|---|---|
| **원시값** | 스택에 **값 직접** 저장 | number, string, boolean, null, undefined, symbol, bigint (크기 고정) |
| **객체·배열·함수** | 힙에 저장하고 스택엔 **주소(참조)만** | 크기 가변 |

```js
// 원시값 → 값 복사
let a = 10;
let b = a;   // b는 10을 복사. a와 무관

// 객체 → 주소 복사
let obj1 = { x: 1 };
let obj2 = obj1;   // 둘이 같은 걸 가리킴 = 얕은 복사
obj2.x = 99;       // obj1.x도 99 (같은 힙 객체)
```

> ※ V8 실제 동작은 최적화가 많아 **개념 모델**임. 면접 답변은 이 모델로.

## 스택 오버플로우

스택은 **크기가 정해져 있음.** 재귀 함수가 종료 조건 없이 계속 자기를 부르면 호출 프레임이 스택에 계속 쌓여 한계를 넘음 → `Maximum call stack size exceeded`.

> 힙은 커서 잘 안 터지지만, **스택은 작아서 깊은 !재귀!에서 터짐.**

## Mark & Sweep GC

가장 단순한 방식인 **참조 카운팅**은 순환 참조(A↔B 서로 참조)를 못 지움. 그래서 **도달 가능성(reachability)**으로 판단:

1. **Mark**: 루트(전역·콜 스택)에서 참조를 타고 **닿을 수 있는 객체를 "살아있음"으로 표시**.
2. **Sweep**: Mark에서 표시 안 된 것 = 아무도 못 닿는 것 = **쓰레기 → 회수**.

> 기준이 "참조 개수"가 아니라 **"루트에서 닿느냐"**라서 순환 참조도 통째로 지워짐.
> (V8은 세대별 GC 최적화를 얹지만 원리는 이거)

## 클로저가 힙에 남는 이유 + 메모리 누수

함수가 끝나면 보통 그 스택 프레임(지역변수)은 사라져야 함. 근데 **내부 함수가 외부 변수를 참조한 채 밖으로 나가 살아남으면(클로저)**, 그 변수는 여전히 도달 가능해서 GC가 못 지움. → 스택이 아니라 **힙에 클로저 스코프(V8의 Context 객체)로 올라가 유지됨.**

```js
function counter() {
  let count = 0;              // 원래는 함수 끝나면 사라져야 할 지역변수
  return () => ++count;       // 근데 이 함수가 count를 물고 밖으로 나감
}
const inc = counter();        // count는 힙에 살아남음 (클로저)
inc(); // 1
inc(); // 2
```

이게 나쁘게 작동하면 **메모리 누수**: 안 쓰는데도 클로저·전역 변수·떼어낸 DOM 노드가 계속 참조를 붙들면 GC가 못 치워서 메모리가 계속 쌓임.

> 흔한 원인: **이벤트 리스너 안 지우기, 클로저에 큰 객체 물고 있기.**

## 한 줄로 꿰기

프로그램 → 실행되면 **프로세스**(격리·무거움) → 그 안에 **스레드**(공유·가벼움) → 공유하니까 **데이터 레이스** → **락**으로 막음 → 락 때문에 **데드락** → JS는 **싱글스레드**라 이 문제 자체가 없음(대신 **블로킹**) → **비동기·Web Worker**로 해결 → 메모리는 **스택**(스레드별)·**힙**(공유)으로 나뉨 → 힙은 **GC**가 도달 가능성으로 청소 → **클로저**는 참조 살아있어 힙 잔류(관리 못 하면 **누수**).
